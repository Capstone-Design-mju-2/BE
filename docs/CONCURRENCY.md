# 재고 동시성 실험 기록

5단계 락 비교의 기준선이다. 같은 시나리오로 방식별 결과를 이 표에 이어 적는다.

## 시나리오

- 재고 1개인 옵션 하나에 1개씩 주문 5건을 동시에 보낸다.
- 모든 주문이 재고 확인을 통과한 뒤 동시에 차감하도록 출발선(`CyclicBarrier`)을 둔다. 경쟁 구간을 매번 같게 만들어 결과가 흔들리지 않게 하기 위해서다.
- 테스트: `OversellReproductionTest`
- 출발선 위치: `none`·`optimistic`은 재고 확인 뒤, `pessimistic`·`redisson`은 락 요청 직전. 락을 잡은 채 출발선에서 기다리면 나머지가 락에 막혀 모이지 못하기 때문이다.

## 결과

| 방식 (`order.stock-strategy`) | 초기 재고 | 동시 주문 | 성공 | 실패 (사유) | 초과 판매 | 최종 재고 |
|---|---|---|---|---|---|---|
| `none` (락 없음) | 1 | 5 | 5 | 0 | 4 | 0 |
| `pessimistic` (`SELECT FOR UPDATE`) | 1 | 5 | 1 | 4 (`OUT_OF_STOCK`) | 0 | 0 |
| `optimistic` (버전 컬럼) | 1 | 5 | 1 | 4 (`OUT_OF_STOCK`) | 0 | 0 |
| `redisson` (Redis 분산 락) | 1 | 5 | 1 | 4 (`OUT_OF_STOCK`) | 0 | 0 |

## 해석

- 5건이 모두 "재고 1개 ≥ 주문 1개" 확인을 통과한 뒤 각자 `quantity = 0`을 저장했다.
- 뒤 주문이 앞 주문의 차감을 덮어써서(갱신 손실), 5개가 팔렸는데 재고는 1개만 줄었다.
- 실제 부하에서 얼마나 자주 나는지는 부하 테스트 단계에서 따로 잰다. 이 표는 "락이 없으면 초과 판매가 난다"를 매번 같은 조건으로 보이는 기준선이다.
- 비관적 락은 확인과 차감 사이에 다른 주문이 끼어들지 못하게 막아서, 뒤 주문들이 차감된 재고(0)를 보고 품절로 끝났다.
- 낙관적 락은 5건이 모두 확인을 통과했지만, 버전이 바뀌지 않은 1건만 차감에 성공했다. 나머지는 재고를 다시 읽어 품절로 응답했다.
- 낙관적 락은 JPA `@Version` 대신 버전 컬럼을 쿼리에서 직접 비교한다. `@Version`을 쓰면 `none`의 UPDATE에도 버전 검사가 붙어 기준선이 사라지기 때문이다.
- Redisson은 DB 쪽 보호 없이 `none`과 같은 확인·차감 코드를 쓴다. Redis 락만으로 초과 판매를 막는지 보기 위해서다. 락은 트랜잭션이 커밋된 뒤에 푼다. 차감 직후에 풀면 다음 주문이 커밋 전 재고를 읽어 초과 판매가 다시 생긴다.

## 부하 측정

### 조건

- 실행 중인 order-service에 `scripts/bench_orders.py`로 주문을 보낸다. 모든 요청이 같은 옵션 하나를 1개씩 주문해 한 행에 경쟁이 몰린다.
- 동시 요청 50개(파이썬 스레드), 서버 DB 연결 풀 10개. 본 측정 전에 다른 상품으로 200건 워밍업한다.
- 로컬 Mac 한 대에서 클라이언트·서버·PostgreSQL(Docker)을 같이 돌렸다. 절대 수치보다 방식 사이의 차이를 본다.
- 방식마다 1회 측정했다.
- 재고 오차 = 남은 재고 − (처음 재고 − 생성된 주문 수). 0이 아니면 갱신 손실이다.
- 성공 처리량 = 성공 수 ÷ 전체 소요 시간. 실패 응답은 빨리 끝나서 전체 TPS를 부풀리므로 따로 계산했다.

### 재고 충분 (재고 1000, 요청 1000)

| 방식 | TPS | 성공 처리량 | p50 (ms) | p95 (ms) | 성공 | 실패 (사유) | 초과 판매 | 재고 오차 |
|---|---|---|---|---|---|---|---|---|
| `none` | 1616 | 1616 | 29 | 44 | 1000 | 0 | 0 | 893 |
| `conditional` | 721 | 721 | 65 | 91 | 1000 | 0 | 0 | 0 |
| `pessimistic` | 737 | 737 | 66 | 79 | 1000 | 0 | 0 | 0 |
| `optimistic` | 1131 | 311 | 44 | 53 | 275 | `CONCURRENT_UPDATE` 725 | 0 | 0 |

### 재고 부족 (재고 50, 요청 200)

| 방식 | TPS | p50 (ms) | p95 (ms) | 성공 | 실패 (사유) | 초과 판매 | 재고 오차 |
|---|---|---|---|---|---|---|---|
| `none` | 1838 | 24 | 30 | 200 | 0 | 150 | 30 |
| `conditional` | 1920 | 15 | 59 | 50 | `OUT_OF_STOCK` 150 | 0 | 0 |
| `pessimistic` | 1665 | 19 | 59 | 50 | `OUT_OF_STOCK` 150 | 0 | 0 |
| `optimistic` | 1027 | 45 | 59 | 50 | `CONCURRENT_UPDATE` 140, `OUT_OF_STOCK` 10 | 0 | 0 |

### 해석

- `none`은 가장 빠르지만 틀린다. 재고 충분에서 1000개를 팔고도 재고가 107개만 줄었고(재고 오차 893), 재고 부족에서는 50개 재고로 200건을 팔았다(초과 판매 150).
- `conditional`과 `pessimistic`은 초과 판매와 재고 오차가 모두 0이고, 성공 처리량도 비슷하다(721, 737). 둘 다 같은 행을 한 번에 하나씩 고치기 때문이다. `pessimistic`은 행을 읽는 순간부터 잠가서 p95가 조금 더 낮게 나왔지만, 1회 측정이라 차이가 의미 있는지는 반복 측정으로 확인해야 한다.
- `optimistic`도 초과 판매는 0이지만, 한 행에 경쟁이 몰리면 대부분 충돌한다. 재고가 충분한데도 725건이 `CONCURRENT_UPDATE`로 실패해 성공 처리량이 311로 가장 낮다. 재시도 없이는 인기 상품처럼 한 옵션에 주문이 몰리는 상황에 맞지 않는다.
- 재고 부족에서 `optimistic`의 실패가 대부분 `CONCURRENT_UPDATE`인 이유: 충돌한 시점에는 재고가 남아 있었고, 재고가 0이 된 뒤에 읽은 10건만 `OUT_OF_STOCK`이 됐다.

## Redisson 비교

비관적·낙관적·Redisson을 같은 날 같은 조건으로 다시 쟀다. 위 "부하 측정"과 조건은 같고, Redis는 `compose.yaml`의 `redis` 컨테이너를 쓴다. 락 대기 시간 3초(`order.redisson.wait-millis`), Redis 명령 타임아웃 1초(`order.redisson.timeout-millis`).

### 재고 충분 (재고 1000, 요청 1000)

| 방식 | TPS | 성공 처리량 | p50 (ms) | p95 (ms) | 성공 | 실패 (사유) | 타임아웃 (`LOCK_TIMEOUT`) | 초과 판매 | 재고 오차 |
|---|---|---|---|---|---|---|---|---|---|
| `pessimistic` | 718 | 718 | 66 | 82 | 1000 | 0 | 0 | 0 | 0 |
| `optimistic` | 1099 | 319 | 46 | 56 | 290 | `CONCURRENT_UPDATE` 710 | 0 | 0 | 0 |
| `redisson` | 389 | 389 | 117 | 195 | 1000 | 0 | 0 | 0 | 0 |

### 재고 부족 (재고 50, 요청 200)

| 방식 | TPS | p50 (ms) | p95 (ms) | 성공 | 실패 (사유) | 타임아웃 (`LOCK_TIMEOUT`) | 초과 판매 | 재고 오차 |
|---|---|---|---|---|---|---|---|---|
| `pessimistic` | 1716 | 17 | 57 | 50 | `OUT_OF_STOCK` 150 | 0 | 0 | 0 |
| `optimistic` | 1295 | 38 | 51 | 50 | `CONCURRENT_UPDATE` 115, `OUT_OF_STOCK` 35 | 0 | 0 | 0 |
| `redisson` | 638 | 61 | 122 | 50 | `OUT_OF_STOCK` 150 | 0 | 0 | 0 |

### Redis 장애

`redisson`으로 띄운 order-service는 그대로 두고 Redis 컨테이너만 멈췄다가 다시 켰다. 재고 50, 요청 200, 워밍업 없음.

| 상황 | TPS | p50 (ms) | p95 (ms) | 성공 | 실패 (사유) | 초과 판매 | 재고 오차 |
|---|---|---|---|---|---|---|---|
| Redis 중단 | 2 | 26096 | 27439 | 0 | `LOCK_UNAVAILABLE` 200 | 0 | 0 |
| Redis 재시작 후 (서비스 재시작 없음) | 615 | 66 | 117 | 50 | `OUT_OF_STOCK` 150 | 0 | 0 |

- Redis가 없는 상태로 order-service를 `redisson`으로 시작하면 약 6.6초 뒤 `RedisConnectionException: Unable to connect to Redis server`로 기동에 실패한다.

### 해석

- 세 방식 모두 초과 판매와 재고 오차가 0이다. 락 대기 시간 3초 안에 모두 락을 얻어 `LOCK_TIMEOUT`도 0건이다.
- `redisson`이 가장 느리다. 재고 충분에서 성공 처리량 389로 `pessimistic`(718)의 절반 정도이고 p95는 195ms다. 주문마다 Redis에 락을 잡고 푸는 왕복이 더해지고, 커밋이 끝날 때까지 락을 쥐기 때문이다. 서버가 한 대뿐인 지금 구조에서는 DB 락만으로 충분하고, Redis 락의 이점은 서버를 여러 대로 늘렸을 때 DB 밖에서 순서를 정해야 할 때 생긴다.
- Redis가 멈추면 주문을 모두 `LOCK_UNAVAILABLE`(503)로 거절해 초과 판매는 0이다. DB 락으로 몰래 넘어가지 않도록 일부러 거절하게 했다.
- 대신 거절하는 데 요청 하나에 26초가 걸렸다. 원인은 두 가지로 추정한다. 첫째, Redisson이 연결 실패 후 바로 포기하지 않고 재시도해서 락 시도 한 번이 1초 타임아웃보다 길어진다. 둘째, DB 트랜잭션을 연 뒤에 Redis 락을 잡아서 Redis를 기다리는 동안 DB 연결(10개)을 쥐고 있고, 나머지 요청은 DB 연결을 기다리며 줄을 선다. 두 원인의 비중은 아직 따로 재지 않았다.
- Redis를 다시 켜면 서비스를 재시작하지 않아도 바로 정상으로 돌아왔다.

### 개선 후보

- 락을 DB 트랜잭션 밖에서 먼저 잡고, 잡은 뒤에 트랜잭션을 연다. Redis를 기다리는 동안 DB 연결을 쥐지 않게 된다.
- Redisson 재시도 횟수와 간격을 줄여 Redis 장애 시 빨리 거절한다.
- 두 가지를 적용한 뒤 같은 "Redis 중단" 시나리오로 다시 잰다.
